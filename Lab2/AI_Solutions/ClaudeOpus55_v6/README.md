# v6 — 合併、拆分、鄰近改接（以 v5 為基礎）

> **這個版本已經併入 `MyCode/v5_balanced_swap` 和 `M11502102`，成為新的 v5。** 下面表格中的「v5」指的是舊版 v5（git commit `917e29a`）。報告用的正式數字在 `Report/tables/`。

以 `MyCode/v5_balanced_swap`（＝交出去的 `M11502102`）為基礎改寫，仍然是單一檔案 `src/main.cpp`，建樹方法和 v5 完全相同，只改了最佳化階段和時間上限。

## 編譯與執行

```bash
cmake -S . -B build
cmake --build build
./build/cbi INPUT_FILE OUTPUT_FILE [-t 秒數] [-s 亂數種子]
```

- 前兩個參數和 v5 相同；`-t`、`-s` 可省略，評分機只會給前兩個參數。
- 預設時間上限：N ≤ 12 為 5 秒，其他為 `min(45, 10 + N/100)` 秒（v5 是 `min(40, 2 + N/250)`）。
- stdout 印 `T_max: X, T_min: Y, Score: Z`，stderr 印各階段紀錄。

## 和 v5 相比改了什麼

| 改動 | 內容 | 程式位置 |
|---|---|---|
| **Merge（合併）** | 把鄰近 buffer `b2` 的所有 children 搬到 `v` 底下，刪掉 `b2`（一半機率再把 `v` 移到平衡位置）。三分之一機率 `b2` 取 `v` 自己的 child，等於把中間那層拿掉 | `optimize` 的 `move == 5` |
| **Split（拆分）** | 從 `v` 的 children 中挑彼此靠近的一群，交給新 buffer，新 buffer 接在 `v` 或 `v` 的 parent 底下 | `optimize` 的最後一個分支 |
| **鄰近改接與交換** | v5 的 Reparent / Swap 只能換到「叔叔」節點。v6 有一半機率改用 `nearNode`：往上走 1～3 層再隨機往下走，可以換到樹上距離較遠但空間相近的 buffer。用 `isAncestor` 檢查不會形成環 | `nearNode`、`move == 2`、`move == 4` |
| **修正最佳解保存** | v5 只在每 1024 步檢查時把「當下的樹」存成最佳解，這時樹可能已經離開最佳狀態，所以存下的解可能比真正找到的最佳解差。v6 在找到更好的解時就保存（大型測資限制保存頻率，避免複製整棵樹太花時間） | `accept` |
| **時間上限** | `min(40, 2 + N/250)` → 小測資 5 秒，其他 `min(45, 10 + N/100)` 秒。最長 45 秒，低於 60 秒限制 | `main` |

Move 比例：Pad 15%、Shift 25%、Reparent 25%、Replace 8%、Swap 8%、Merge 9%、Split 10%。

## 結果

測資 A = `Testcases/testcases`（15 筆），測資 B = `Testcases/holdout`（12 筆）。
v5、v6 各跑 2 次取平均，輸出全部通過課程 verifier（VALID）。數字是 Score 的幾何平均比值，越小越好。

| 比較 | A 組 | B 組 |
|---|---|---|
| **v6 / v5（最終版）** | **0.876（好 12.4%）** | **0.847（好 15.3%）** |
| v6 用 v5 的時間上限 / v5 | 0.902（好 9.8%） | 0.871（好 12.9%） |
| v6 不含 Merge、Split，用 v5 的時間上限 / v5 | 0.923（好 7.8%） | 0.930（好 7.0%） |
| v5 / v1（報告中的版本比較） | 0.473 | 0.306 |
| v6 / v1 | 0.414 | 0.259 |

由此可拆出各項改動的貢獻（約略值）：

- 鄰近改接、交換與最佳解保存修正：約 7～8%
- Merge 和 Split：A 組約 2%，B 組約 6%
- 時間上限放寬：約 2.5%

同一個版本跑兩次的差異約 ±1%，所以小於 1% 的差距不能視為有效改善。v6 沒有任何一筆測資比 v5 差（A-001、A-014、B-001 三筆持平）。

### 和 `ClaudeOpus55Ultracode_3` 比較

Ultracode_3 仍比 v6 好約 3.5%（A 組 0.967、B 組 0.962）。它用了 11 種 move、2 條執行緒，程式約 2,700 行；v6 約 950 行，結構和 v5 相同，比較容易在報告中說明。

## 試過但沒有採用的

| 方法 | 結果 |
|---|---|
| 建樹時改用「每單位 fanout 成本最低」的切法 | 初始解有好有壞，最佳化後和 v5 的切法差不到 0.1% |
| 針對最早到達路徑計算繞路長度的 Pad | 在 ±1% 雜訊內 |
| 調整 move 比例（更多 Merge/Split、更少 Pad） | 在 ±1% 雜訊內 |
| 起始溫度 ×0.5、×2 | A、B 兩組方向相反，沒有一致的改善 |
| 2 條執行緒，每 1/4 時間同步一次 | A 組 0.0%、B 組 0.5%，在雜訊內 |
| 退火前先插繞路 buffer 平衡 skew | 起點 Score 大幅下降，但最佳化後 A 組 +0.2%、B 組 −1.1% |
