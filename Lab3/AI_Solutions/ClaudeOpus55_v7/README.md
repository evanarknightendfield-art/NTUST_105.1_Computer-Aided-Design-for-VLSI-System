# ClaudeOpus55_v7

以 CodexParallelChain（CPC）為底。先量 CPC 哪裡不足（[diagnosis.md](../../Testcases/results/ClaudeOpus55_v7/diagnosis.md)），
再依「幅度 × 機會」改了四項。最終數字全部來自同一段時間、同一台機器的配對重跑
（[final/summary.md](../../Testcases/results/ClaudeOpus55_v7/final/summary.md)，2026-10-24 05:55–11:05）；過程與每一步的數據在 [WORK_STATE.md](WORK_STATE.md)。

編譯與執行跟前幾版一樣：`cmake -S . -B build && cmake --build build`，`./build/dp INPUT OUTPUT`（或 `make`）。

## 1. 診斷摘要（第一階段）

| 發現 | 數據 |
|---|---|
| **大設計的 Stage 1 有牆鐘斷崖**：pareto 只在第 100 秒前開始；前一步（total-refine 每 256 個 cell 才看一次時間，L2 上一輪不看時間 10 秒）晚 1 秒結束，pareto 就整段不跑 | L2 HPWL +7%、總位移 +1.8%、最大 +2.5%（4 / 2 核時發生；最終驗證時 CPC 在全核也發生 1 次） |
| **大設計的 Stage 1 時間給錯步驟**：L2 約 75 秒花在每秒 0.004–0.016% 的串行步驟，pareto（0.13%/秒）與視窗 DP（0.10%/秒）幾乎沒拿到時間 | 只加 `--no-rowopt` 的探測：L2 總 −2.0%、最大 −3.3%、HPWL −3.2%、快 13 秒 |
| **少核心時執行緒跟著變少**：CPC 開 min(8, 硬體執行緒) | 2 顆 P-core：SA 8 執行緒比 2 執行緒多 28% 次數、h08 HPWL −1.6%；L1 總位移 −3% |
| **pareto 之後的主視窗 DP 重解沒變的視窗**（finish() 的 memo 是區域變數） | 27 筆主 DP 32.4 秒，7 筆 0 改善仍花 0.1–1.1 秒 |
| **L2 額外步驟超出 6 秒預算**（cap 搜尋的修復在 1M cell 上比期限多 1.1–1.5 秒） | 4 / 2 核 6.20 / 6.17 秒；最終驗證全核 6.36 / 6.39 / 5.05 秒 |
| h06 最大位移雙峰 | 427.55 或 435.19：cap 搜尋的 DP 跑 4.0 秒就接受、3.35 秒就被總位移上限拒絕，是牆鐘造成的 |
| chain 階段重新分配、SA / polish 分配、視窗 DP 尾巴提早停、平行 SA band | 都量了，沒有可拿的收穫（第 4 節） |

## 2. 改了什麼（第二階段）

| 項目 | 改動 | 檔案 |
|---|---|---|
| A 大設計 Stage 1 排程 | refinement 的 pipeline 用完自己的份額（= 這台機器上這個設計在 Stage 1 預算內做不完）時，跳過 finish() 的回合，直接 pareto + 視窗 DP；依量到的是否趕上期限，不依 cell 數。期限檢查變細：total-refine 每 16 個 cell、row-opt 每個 segment、matching sweep 每個視窗、過期限的 pass 不開始。pareto 的 group 平行（group 之間不共用 cell，結果與執行緒數無關），第一輪一定跑、之後的輪每 4096 個 group 看一次期限 | `legalizer.cpp`、`optimizer.cpp`、`main.cpp` |
| B 執行緒 | 自動模式固定 8 個 worker（DP、pareto、SA）；SA 在受記憶體上限的大設計（2e6 / (cell+net) < 8）不超過這個行程能用的 CPU（`availableCpus()` = sched_getaffinity，taskset / cpuset 看得到） | `main.cpp`、`annealer.cpp`、`placedb.cpp` |
| C memo | finish() 的視窗 memo 交給 main 的 stage1Memo，主視窗 DP、chain 後 DP、cap 搜尋只重解變過的視窗（結果不變） | `legalizer.cpp`、`main.cpp` |
| D 額外步驟保留量 | cap 搜尋記下修復比期限多跑多久（量到的固定開銷），只在剩餘時間 ≥ 門檻 + 這個量時才開始下一次嘗試與最後的清理 | `capsearch.cpp` |
| 量測用 | `--trace-dp`、`--chain-split`、`[chain-phase]` 摘要行（預設不影響）；`tests/sa_bench2.cpp --starved` | `main.cpp`、`window.cpp` |

測試：新增 pareto 平行與執行緒數無關、過期限只跑一輪（`optimizer_test`）、`availableCpus` 跟著 affinity（`pool_test`）。
一般、ASan+UBSan（detect_leaks=1）、TSan 各 10 個程式 28 項全過，無 sanitizer 警告（`phase2/tests/B2`）；
固定次數下同 seed、同執行緒數（4 / 自動）兩次的 .pl 逐位相同（`phase2/determinism`）。
凍結：`Testcases/results/ClaudeOpus55_v7/frozen_sources.sha256`（53 檔），之後原始碼沒有再改。

## 4. 試過沒用、沒有做的

| 方向 | 數據 | 決定 |
|---|---|---|
| chain 階段時間重新分配（ejection 少給、DP / windows 多給） | target windows 與之後的 DP 在自己的份額內就收斂：ejection 0 / 0.1 / 0.25 → chain 後總位移 GM +0.017 / +0.0075 / +0.0003%（11 筆），4 輪 +0.035%；只是讓 chain 提早結束 | 不做 |
| 平行 SA 的 band 邊界（輪替後 0.63%，ibm01 2.46%） | 預設 60 秒時 8 band 對 4 band：ibm01 −0.6%、h07 / h08 −1.0%、ibm05 / h06 0 → 邊界損失不是瓶頸 | 不做 |
| 中型設計 SA / polish 分配 | SA 越多越好：SA 20 + polish 2 優於 SA 5 / 10；預設 SA 60 + polish 30 優於 SA 30 + polish 60（1.0–3.2%） | 不改 |
| 視窗 DP 尾巴依收穫提早停 | 「總位移 ≤ 最終 ×1.0001」就停只省 16.9 秒（27 筆），可省的多半是重解 → 改用 C | 併入 C |
| SA 在少核心時也固定 8 worker（B 第一版） | 2 核上 L1（受記憶體上限、SA 4 worker）HPWL +1.38%：只多 6% 次數、band 邊界加倍 | 改成 B2（受記憶體上限時 ≤ 可用 CPU） |

對 CPC 的驗收沒達到的：

- 27 筆雙條件 20 vs CPC 21（e15，見上）；總位移 GM 0.99986 vs 0.99977（+0.009%，在 Stage 1 執行間變動 0.11% 內，但不能說不比 CPC 差）。
